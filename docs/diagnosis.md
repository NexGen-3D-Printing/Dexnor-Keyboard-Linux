# Diagnosis

How the two fixes were found, with the actual evidence. Both devices were
observed on Fedora 44 KDE (kernel `7.2.14-1.surface.fc44.x86_64`, BlueZ
5.87) with a Dexnor Bluetooth keyboard/touchpad combo, HID
`0005:05AC:0220`.

The same hardware works perfectly on Windows 11 on the same machines, which
ruled out a hardware or firmware fault early.

---

## 1. Dropped keystrokes — PPCP latency

### Symptom

Typing quickly on either of two identical keyboards dropped random
characters. Slow typing was fine. Re-pairing, battery changes, and moving
the receiver made no difference.

### Capture

`sudo btmon` during a reconnect shows the connection parameters BlueZ
selects:

```
> HCI Event: LE Meta Event (0x3e) plen 19
      LE Connection Complete (0x01) status 0x00
      ...
> HCI Event: LE Meta Event (0x3e) plen 14
      LE Connection Update Complete (0x03) status 0x00
      Connection interval: 7.50 msec (0x0006)
      Connection latency: 35.00 msec (0x0023)
      Supervision timeout: 2000 msec (0x00c8)
```

Latency 35 with a 7.5 ms interval means the peripheral may skip 35 of every
36 connection events. That is a worst case of roughly **270 ms** between
chances to deliver a HID report — long enough to lose press/release pairs
during fast typing.

### Where it comes from

The keyboard exposes the standard GAP **PPCP** characteristic (`0x2A04`):

```
min interval     6  (7.5 ms)
max interval     6  (7.5 ms)
latency         35
supervision    200  (2000 ms)
```

BlueZ 5.76+ reads PPCP in `profiles/gap/gas.c:read_ppcp_cb()` and applies
it through `btd_device_set_conn_param()`. Latency 35 is legal, so BlueZ
accepts it. Windows does not apply PPCP, which explains the platform
difference.

### Fix

Re-issue `LE Connection Update` with `latency = 0`, keeping the keyboard's
own interval so it accepts the request:

```
min=6  max=6  latency=0  timeout=200
```

`bt-keyboard-latency.py` does this over the raw HCI socket
(`hci_le_conn_update`) and re-applies it on every connect. The
`[ConnectionParameters]` section in the BlueZ info file makes the boot-time
default correct as well.

### Confirm

```
> HCI Event: LE Meta Event (0x3e) plen 14
      LE Connection Update Complete (0x03) status 0x00
      Connection interval: 7.50 msec (0x0006)
      Connection latency: 0.00 msec (0x0000)
      Supervision timeout: 2000 msec (0x00c8)
```

After that, fast typing stopped dropping keys on both keyboards.

## 2. Touchpad click — latched `BTN_LEFT`

### Symptom

Pressing the touchpad until it physically clicked produced no click until
the finger moved. Tap-to-click worked normally, and so did two-finger
scroll and right-click.

### HID report layout

The combo exposes several HID reports. The touchpad is report 6
(Digitizer/TouchPad). Its final byte carries the physical button as bit 0:

```
byte 0..N-1 : contact count, X/Y, pressure, ...
byte N      : bit 0 = physical button (BTN_LEFT)
```

The kernel's `hid-multitouch` maps that bit to `BTN_LEFT`.

### Capture

Reading the raw reports while pressing and releasing the pad:

```
913.572686  count=1  btn=1   finger lifting
913.579631  count=0  btn=1   contact ended, button STILL 1
913.587630  count=0  btn=1   last report, button STILL 1
   ... 7.2 seconds of silence ...
920.757830  count=1  btn=0   next touch finally clears it
920.787562  count=1  btn=1   then presses again
```

The button bit is set on press, but the firmware never clears it on
release. It stays `1` until the first report of the next touch. The evdev
node shows the same thing: `BTN_LEFT` stays down across contact end.

Most toolkits (and libinput's click handling) act on button **release**.
Since no release arrives, the click never completes — until the next touch
clears the latched bit, which is why moving the finger "fixes" it.

### Why not patch the kernel?

The report layout is device-specific and the firmware is arguably
malformed. A kernel quirk would be one option, but it is harder to ship,
needs a rebuild, and breaks on kernel updates. `input-remapper` was also
tried and rejected: it adds a configuration layer, does not help when the
release never arrives, and interferes with the desktop's own settings.

### Fix

A userspace daemon that:

1. Finds the physical device by name and sysfs path (`/uhid/`), so it does
   not grab its own clone.
2. Grabs it and forwards every event unchanged to a uinput clone with the
   same name, IDs and `INPUT_PROP_BUTTONPAD`.
3. Watches for the end of the last contact (`BTN_TOUCH=0`, or the last
   `ABS_MT_TRACKING_ID=-1`). If `BTN_LEFT` is still held, it emits the
   missing `BTN_LEFT=0`.

Because the clone is what the desktop sees, libinput and KWin apply their
normal settings to it. Tap-to-click is generated by libinput from touch
events and never uses `BTN_LEFT`, so it is unaffected.

### Confirm

A synthetic end-to-end test fed the daemon a contact plus a latched button
and read back the clone:

```
clone BTN_LEFT sequence: [1, 0]
```

KWin's log then showed it using the clone:

```
kwin_wayland: Libinput: event20 - Dexnor Keyboard Touchpad: ...
```

A physical press-and-release now fires the click immediately.

---

## Environment notes

- Input node numbers change on every reconnect. The daemons re-scan by name
  and sysfs path rather than hardcoding `eventN`.
- SELinux was Enforcing during testing with no denials for either service.
- `python3-evdev` is required for the touchpad daemon; `python3-dbus` and
  `python3-gobject` are required for the keyboard daemon.
